# What Bonsai does

Every capability Bonsai has, by area: what it does for you, how you use it, and where it stops. Each area ends at its
limits, with the open bugs that touch it linked to the register, [`records/bugs.md`](../records/bugs.md); the page
closes with what Bonsai does not do at all. It is written from Bonsai's code on `main`; a row marked
*from 1.0.0-rc.2* is on `main` and not in 1.0.0-rc.1.

Where a capability rests on a list (rule words, check words, secret kinds), this page names it and links the list in
[`docs/reference/lists.md`](reference/lists.md), which is generated from the code: every list has one home.

## Setting up

One Go program links a git checkout to Bonsai and to packs: Claude Code plugins with a small manifest Bonsai reads.
Everything Bonsai writes into the project is previewed first and recorded in a lock, so it can be checked offline,
updated and taken out again.

| Capability | What it does for you | How | Limits |
|---|---|---|---|
| Link a project | Writes `bonsai.yaml` (a comment on every line), the packs' files, a block in `CLAUDE.md`, Bonsai's lines in `.claude/settings.json` (hook lines, deny rules, plugin wiring), `.bonsai/` (STATE, the two tables, a `.gitignore`) and the lock, last | `bonsai init --name <name> --source <git URL> --ref <tag or commit> [--path <folder>] --yes` | It previews by default: at a terminal it asks; with none it prints the preview and exits 4 (`needs-yes`), writing nothing. A git checkout only (`not-a-checkout`). A pack that carries code also needs `--allow-exec`, which only a person types (below). None known |
| Keep packs at their refs | Fetches each pack at the ref in `bonsai.yaml` and decides each file from three fingerprints (the lock's, the disk's, the pack's): unchanged, updated, created, your edit left alone, or a conflict. It lists every file and settings line it adds, changes or removes, each with a sentence | `bonsai update [--yes] [--diff] [--explain] [--keep <path>] [--adopt <path>]` | All or nothing: any conflict writes nothing (exit 5) until you settle it with `--keep` (your edit) or `--adopt` (the pack's copy; yours is saved in Bonsai's home). A tag that moves to another commit is refused (`tag-moved`). Packs are added or taken out by editing `packs:` in `bonsai.yaml`; there is no command for it. [BUG-017](../records/bugs.md): `--json` carries nothing for update's memory and cache-clean lines |
| Consent to code | Code that will run on your machine (a pack's hook lines and the files they run, a plugin's hooks, MCP servers and monitors) is written only with `--allow-exec` as well as `--yes`, even at a terminal | `bonsai update --allow-exec --yes`, typed by you | Refused in an agent's session (`person-command`, exit 4), by the command itself and by the guard. A plugin with code waits (`waiting`) on each machine until a person gives it. None known |
| Take Bonsai out | Removes the files the packs wrote that you did not edit, the block in `CLAUDE.md`, Bonsai's settings lines, the tables, `bonsai.yaml` and the lock; uninstalls the packs' plugins for this checkout. Run again, it changes nothing | `bonsai unlink --yes` (a person's command) | Leaves and names your edited files, `.bonsai/STATE.md` and `.bonsai/local/`. A plain `git revert` of the link commit leaves Claude Code's plugin record behind. [BUG-020](../records/bugs.md): unlink leaves this machine's folder for the checkout in Bonsai's home |
| `bonsai.yaml`, the settings | The one Bonsai file you edit: the packs and their refs, where each kind of document lives, the protected and person-only paths, paths no agent may ever edit, the ladder, its floor and ratchets, how long generated files are kept, your limits for the packs' roles, the message flags' thresholds | Edit it by hand; `bonsai check --schema bonsai.workspace` prints every field; the skill `base:workspace` explains each | Person-only: the guard refuses an agent's edit unless a person granted it. Unknown fields are kept, a duplicate key refused. The ladder reads it only as committed, and a change that loosens a check waits for you ([the ladder](#the-ladder)). In the JSON schema, a rung's `ratchet` and `capture` are typed open, so a schema-only reader accepts shapes Bonsai refuses. None known |
| The lock | `.bonsai/lock.json` records each pack's source, commit and what it declares, and every file Bonsai wrote with its kind and fingerprint, so `bonsai check` works with no pack fetched | Written by `init` and `update` only; `bonsai check --schema bonsai.lock` | Person-only. A missing or unreadable lock is a person's step (`no-lock`, `bad-lock`). [BUG-055](../records/bugs.md) |
| Packs are Claude Code plugins | After `init` and `update` Bonsai asks Claude Code to install each pack as a project-scope plugin at its locked commit, and reports each one: installed, waiting, failed, skipped or uninstalled ([plugin results](reference/lists.md#plugin-results)) | Automatic; `bonsai status --full` shows what Claude Code reports | Claude Code learns the project's packs only after you open it in the folder and accept its trust question; Bonsai never answers it. The plugin's marketplace name moves with every pack commit, so consent to code is asked again after any pack's update. `skipped` and `waiting` do not change the exit code. None known |
| Write your own pack | A pack is a plugin plus a `bonsai/` folder: `pack.yaml` (files, hooks, deny rules, document kinds, protected paths, roles), labels, lanes, a block for `CLAUDE.md`. `packs/template/` is a minimal valid pack to copy | `bonsai check --pack <folder>` in the pack's CI; `bonsai check --schema bonsai.pack` | `check --pack` holds the pack to its formats with [its own words](reference/lists.md#check---pack-words); a template skill with no fields table is not checked. A pack may not write Bonsai's own files, `CLAUDE.md` or Claude Code's settings. [BUG-025](../records/bugs.md): a pack's relative deny rule does not hold after a shell `cd`. [BUG-083](../records/bugs.md) |
| The `base` pack | Bonsai's own, carrying no code: templates and operating skills for its documents (10 skills), Bonsai's four labels (`bonsai.allows`, `bonsai.wants`, `bonsai.ladder`, `bonsai.branch`), `bonsai.yaml` and the lock as protected paths, and 149 deny rules, the walls ([the guard](#the-guard)) | `--path packs/base` on `bonsai init` | [BUG-035](../records/bugs.md): some agent tools' key files are not walled |
| The `workflow` pack | A team of agents for Claude Code, in its own repository ([`LastStep/bonsai-workflow`](https://github.com/LastStep/bonsai-workflow)): six roles (orchestrator, builder, verifier, researcher, auditor, runner) with their limits, three lanes (light, full, director), eight document kinds (plan, one-pager, decision, options, spec, playtest, daily brief, bugs register), six labels and 19 skills. It carries no code | Add it to `packs:` and run `bonsai update` | Written for a game studio ("the director", "a player"); it works the same for other software. Bonsai itself reads only two lane rules, `approve_first` and `close` ([lane rules](reference/lists.md#lane-rules)). [BUG-013](../records/bugs.md): its verifier and runner cannot make scratch repositories |
| See where a project stands | One workspace at a glance: packs and their state, the active task, its last ladder result, the person-only paths, roles and their limits, problems and what is needed | `bonsai status [--json]`; `--full` adds newer pack and Bonsai releases, the plugins as Claude Code reports them and Claude Code's version; `--active` names the active task | Offline by default; `--full` reaches the network, for Bonsai's releases at most daily (10 s, cached). [BUG-015](../records/bugs.md): a tag counts as a release before it is published |
| This machine's settings | Four keys kept in Bonsai's home, never in the project: who moves a task's status (`status_writes`, `status_command`), how long unused pack clones are kept (`cache_keep_days`) and, on Windows, where the personal memory layer is read from (`personal_from`) | `bonsai settings show [--machine]`; `bonsai settings set key=value [--machine]` (a person's command) | All values are checked first, then all written or none. [BUG-016](../records/bugs.md): a `status_command` can still be a harmful plain command |
| Label definitions without a pack | Adds your own label definitions on this machine from a `bonsai.labels/1` file | `bonsai labels attach <file>`; `bonsai labels detach <namespace>` (a person's commands) | Definitions may be added, never redefined (`label-redefined`): detach first. A namespace a pack holds, or `bonsai`, is refused. `unlink` does not detach. None known |
| Install a signed release | Archives with a checksum file and a build attestation from Bonsai's own release workflow; installers put `bonsai` where only an administrator writes: `/usr/local/bin/bonsai` or `C:\Program Files\Bonsai\bonsai.exe` | [`docs/install.md`](install.md): download, `sha256sum`, `gh attestation verify`, then `install.sh` or `install.ps1` | Needs `gh` 2.97 or newer, logged in. `install.sh` refuses off Linux and as root. Bonsai's hook lines run only the installed copy, never one on the `PATH`, and `bonsai check` finds a `PATH` copy that is not it (`bonsai-path`). [BUG-018](../records/bugs.md), [BUG-019](../records/bugs.md), [BUG-021](../records/bugs.md), [BUG-062](../records/bugs.md) |
| Hear of a newer release | `bonsai check` warns `bonsai-newer`; `bonsai status --full --json` gives the install lines for it | Automatic | [BUG-015](../records/bugs.md) |
| Platforms | Linux, WSL and Windows, on amd64 and arm64; CI runs the tests on Linux and Windows. Release archives are also built for macOS | The installers above | macOS builds are untested and have no installer. On Windows the hook lines run in Git Bash, installed for all users (`git-bash`, `git-user` findings when it is not). [BUG-086](../records/bugs.md) |
| A Bonsai 0.4.3 project | Refused with `old-workspace` (exit 4) by `init`, `update` and `unlink`, nothing read or changed | Automatic | There is no migration from 0.4.3; the refusal says it comes later |

## The guard

Before Claude Code runs an agent's edit or shell command, its hook line runs `bonsai hook guard`, which allows the call
or refuses it with three lines: why, the next step and whether an agent or a person takes it, and the rule. Every
decision goes to the log, except where the session or the path is in no linked project (`not-linked`). The guard has 68 rules ([guard rules](reference/lists.md#guard-rules)).

| Capability | What it does for you | How | Limits |
|---|---|---|---|
| Judge every edit and command | Runs before every `Edit`, `Write`, `MultiEdit`, `NotebookEdit`, `Bash`, `PowerShell` and `Monitor` call, and, where a pack declares roles, every `Agent`, `Task`, `SendMessage` and `Workflow` call ([the tools](reference/lists.md#the-guard-lines-tools)) | Written into `.claude/settings.json` by `init` and `update` | It does not see `Read`, `Grep`, `Glob`, web or MCP calls: reads are stopped only by the walls, below. A session started outside the project's top folder loads none of its settings, so nothing guards it. Your own Claude Code settings, or a mod, can turn hooks off (`bonsai check` finds `disableAllHooks` in the project's settings: `hooks-off`). |
| Fail closed | If the installed `bonsai` is missing or fails, the line refuses every call it judges; the guard times itself at 5 s so a slow check never lets a call through (`over-time`), and a crash is a refusal | Automatic | A broken install blocks all work in the project until it is fixed; reads and searches still pass. Measured with Claude Code 2.1.294 on Windows: a line that cannot start there lets the call through, since that version ignores the line's `onFailure` field |
| Protected paths | A path on `bonsai.yaml`'s `protected` list, or a pack's, is refused to an agent unless the running task's `bonsai.allows` lists it, and only while that task reads `running` | `protected:` in `bonsai.yaml`; `bonsai.allows` on a task | Two tasks reading `running` grant nothing. In the default mode (`status_writes: agents`) an agent that may edit its own task file can grant itself a protected or a person-only path; command mode, below, closes that. [BUG-051](../records/bugs.md): grants are read from the main checkout's working tree |
| Person-only and never-granted paths | Whatever `bonsai.yaml` says, a floor of 14 paths holds in every project: `bonsai.yaml`, the lock and `.bonsai` are person-only (a person's grant opens them); `.claude/settings.json`, `.claude/settings.local.json` and every `.git` are never granted ([the floor](reference/lists.md#the-guards-floor)) | `person_only:` in `bonsai.yaml` adds paths; `bonsai.wants` on a task asks for them | Never-granted paths change only by a person or by `bonsai update`. None known |
| Bonsai's own files | The log, the asks, the ladder results, the messages, the agents' state (`.bonsai/local/`), the generated tables and Bonsai's home are written by Bonsai alone; a file named `bonsai`, `bonsai.exe` and the like outside every project (a stand-in for the program on the `PATH`) is refused | Automatic (`bonsai-files`, `bonsai-stand-in`); `bonsai check --write` rebuilds the tables | [BUG-050](../records/bugs.md): this machine's record of the checkout, in Bonsai's home, is writable by an agent's shell |
| Every name of a path | A path is judged in every form it has: as written, through links, with `~`, and on Windows its `\\?\`, Git Bash `/c/`, stream, trailing-dot and admin-share forms and the final path Windows resolves. Any refused form refuses | Automatic | Not seen: a link swapped between the check and the write, a hard link to a protected file, another machine's share of the disk. [BUG-058](../records/bugs.md), [BUG-086](../records/bugs.md) |
| Shell lines: deletes and moves | Splits a command line into words as its shell would (bash, PowerShell, cmd), never running or expanding anything, and reads through programs that run others (`sudo`, `env`, `xargs` and 25 more, [the list](reference/lists.md#words-that-run-another-program)) and shells given text (`bash -c`, `eval`, `powershell -Command`). A delete or move of a guarded path is refused; so is a bulk delete that does not name what it deletes (a glob, a variable, `.`, `~`, `git clean` with no path) | Automatic; the delete words: [the list](reference/lists.md#delete-words) | A shell write to a protected path (a redirect, `cp`, a script, an interpreter) is not judged for a role that may write: rung 0 of the ladder catches it after. Not seen: a delete a program makes through its own calls, a command built in a variable, an alias defined elsewhere. [BUG-036](../records/bugs.md), [BUG-037](../records/bugs.md), [BUG-038](../records/bugs.md), [BUG-060](../records/bugs.md) |
| A person's own commands | Refuses an agent `bonsai ... --allow-exec`, `bonsai unlink`, a line that unsets or sets one of the variables marking an agent's session (`person-command`), and `bonsai settings set` and `bonsai labels attach`/`detach` (`home-command`). An agent's `init` or `update` is judged as an edit of `bonsai.yaml` and the lock; a preview passes | Automatic; the commands refuse themselves in an agent's session as well, which any of eight markers makes one: Claude Code's `CLAUDE_CODE_CHILD_SESSION`, `AI_AGENT`, pi's `PI_CODING_AGENT`, `CODEX_THREAD_ID`, `GEMINI_CLI`, `CURSOR_AGENT`, `OPENCODE` and `GOOSE_TERMINAL`; the refusal names the one it found | Claude Code's `!` lines count as an agent's session: type these in a terminal of your own. `CLAUDECODE` alone, which an editor's terminal also carries, counts for nothing. Under another agent a marker is a tripwire: an agent that clears it in a shell no guard reads gets past it |
| The walls | Deny rules Claude Code enforces: `base` walls the places that hold keys and logins against reading (`~/.ssh`, cloud and `gh` logins, `.netrc`, Claude Code's own credentials, Bonsai's salt, each also in its WSL and Windows forms) and shell start files, Claude Code's user settings and `~/go/bin` against editing; Bonsai adds walls on its own files; a `never_edit` path becomes a wall anchored at the project's top | Written by `init` and `update` (149 from `base`); `never_edit:` in `bonsai.yaml`, or `--never-edit` on `init` | A tripwire too: a Read rule stops Claude Code's file tools and `cat`, not a script or a program that reads the file itself. On Windows the PowerShell tool ignores Read and Edit deny rules. A project's own `.env` files are not walled. [BUG-025](../records/bugs.md), [BUG-035](../records/bugs.md) |
| Command mode | Where a team moves task statuses through its own command (`status_writes: command` on this machine), the guard refuses an agent's edit that moves a status or lane, puts a person-only path in `bonsai.allows`, sets a label only an outside program sets, or writes a task, run report or STATE that fails its format; each refusal names the command | `bonsai settings set status_writes=command status_command=<command>` | [BUG-016](../records/bugs.md) |
| Roles: who may call whom | Where a pack declares roles: the person's session may start any other role; a lead may start helpers; a helper starts no one. Starting Claude Code from an agent's shell is refused ([the start words](reference/lists.md#claude-codes-start-words)). An agent of a type no pack declares is held as a helper that writes nothing | Roles in the pack's `pack.yaml`; your limits under `packs[].roles` in `bonsai.yaml` | Agents are attributed, not authenticated. [BUG-045](../records/bugs.md) |
| Roles that write nothing | A role declared `writes: false` (in `workflow`: verifier, researcher, auditor, runner) is refused every file edit and every shell write the guard can read into a project: redirects, `cp`, `sed -i`, `git commit` and 40 git words ([the list](reference/lists.md#gits-write-words)) | Automatic | It can still write through an interpreter, a script or an MCP server. A relative write after a `cd` the guard cannot follow (`cd $S && cat > b.py`) is judged in the folder the command started in, so it is refused even when the folder is outside the project; the refusal says so and asks for the file's full path ([BUG-108](../records/bugs.md)). [BUG-039](../records/bugs.md), [BUG-040](../records/bugs.md), [BUG-013](../records/bugs.md) |
| Budgets | Each agent's minutes, actions (refused calls counted) and red climbs in a row are counted; past a limit every call is refused but its report, reading its brief and handing back (`budget-spent`), and the first refusal gives the exact report command. A brief may set limits up to the max in force ([role limits](reference/lists.md#role-limits)) | Automatic; `--budget` on `bonsai message`; reads, searches and skills are counted by a second hook line that fails open | An agent gone quiet makes no call, so nothing stops it. [BUG-041](../records/bugs.md), [BUG-042](../records/bugs.md), [BUG-059](../records/bugs.md) |
| The time check, *from 1.0.0-rc.2* | Refuses an `Edit`, `Write` or `MultiEdit` that puts a fresh time or day into a record stamp (a task's `created`, `started`, `finished`; a run report's `started`, `finished`; STATE's or a memory note's `updated`; a pack kind's stamps) more than 10 minutes from the UTC clock, or a day after the UTC today or more than 2 days before it (`time-not-now`) | Automatic; the next step is `bonsai now` or `bonsai now --day` | `Edit`, `Write` and `MultiEdit` only (not a `NotebookEdit`): a shell write of a stamp, and a correction of a value already there, pass. None known |

## The stop gate

A Claude Code session started with `BONSAI_TASK` set cannot end until the ladder has proven its task at the commit it
ends on. A session started without it is not held.

| Capability | What it does for you | How | Limits |
|---|---|---|---|
| Hold a session until its work is proven | Each time the session tries to end, `bonsai hook stop` checks, in order: the settings read, the main checkout is verified and on its branch, `bonsai.yaml` is committed and no looser than you accepted, the task exists once and reads, a run report for it is in the session's checkout and each of the task's run reports there passes `bonsai check` (*from 1.0.0-rc.3*: no finding of check's on the file, `stop-bad-run-report`), and a ladder result exists that is for this task, local, green, at the checkout's HEAD, with nothing uncommitted and every rung asked for green. The first that fails sends the session back with what is missing | `BONSAI_TASK=T-0001 claude` | Claude Code lets a turn end after eight blocks in a row (`CLAUDE_CODE_STOP_HOOK_BLOCK_CAP` raises it); each block is logged. The task comes only from `BONSAI_TASK`. [BUG-092](../records/bugs.md): a session waiting on an answer to its ask is blocked while red; [BUG-049](../records/bugs.md) |
| Say why, and what next | Each block prints three lines, `bonsai stop gate: <why>.`, `next: <next>.` and `rule: <rule>.`; 22 rule words, from `stop-not-named` to `stop-budget` ([guard rules](reference/lists.md#guard-rules)). Every decision is logged, except where the session is in no linked project (`not-linked`) or names no task (`stop-not-named`) | Automatic | The rule word at the end of every block, and the names `stop-task-unknown` and `stop-rung-not-asked`, are *from 1.0.0-rc.2*. None known |
| A spent budget may stop | A named session whose budget is spent may end with a red ladder once its report exists (`stop-budget`) | Automatic | It can spend its budget on purpose to stop red, but only after writing its report |
| Fail closed | With no installed `bonsai`, every end is refused until Claude Code's cap | Automatic | A broken install holds every named session; [`docs/install.md`](install.md#the-way-out) has the way out |

## The ladder

The ladder runs your project's checks (rungs), cheapest first, and writes one result: the proof a session's stop gate
and a reviewer read. You write the rungs in `bonsai.yaml`; `bonsai init` writes none.

| Capability | What it does for you | How | Limits |
|---|---|---|---|
| Climb | Runs the floor's rungs (`ladder_floor`) plus the task's `bonsai.ladder` rungs, each once, in number order; a required rung that is not green skips the rest. Exit 0 green, 1 red | `bonsai ladder --task <id> [--json]`; `--root <folder>` for another checkout | One climb at a time per Bonsai home: a second waits while the first is within its time, then is refused (`ladder-busy`). Rungs run one at a time. [BUG-094](../records/bugs.md) |
| Three kinds of rung | `command` (a shell command, green on exit 0), `guard` (rung 0, below) and `ver-git` (git integrity, below) | `ladder[].kind` in `bonsai.yaml` | A command may not call `bash` by name (`rung-bash`). A command rung's default time limit is 600 s, rung 0's and git integrity's 120 s; a rung past its limit is red. Its processes end with it (a process group on Linux, a job object on Windows), except what a service manager starts outside it. None known |
| Rung 0: the change stays in its lane | Every change on the branch and in the tree is inside the task's grants; no generated table changed on a branch; nothing in `.bonsai/local/` tracked; no `bonsai check` finding | `kind: guard` | It catches after the fact what the guard does not see before (shell writes). [BUG-048](../records/bugs.md) |
| Git integrity | Records the task's base commit and lists git tricks that would hide a change (assume-unchanged, skip-worktree, a filter, an edited exclude file, a rewritten base): 13 findings ([the list](reference/lists.md#git-integrity-findings)). One that hides a change marks the result dirty | `kind: ver-git` | It never turns red on a finding. A sparse checkout always reads dirty. [BUG-054](../records/bugs.md): Git LFS and git-crypt checkouts always read dirty |
| Tests read by name | Reads a rung's output as `go-test-json`, `tap` or `junit`; keeps the first 50 failing tests, each with the command that runs it alone | `ladder[].tests` | A package that does not build is named and the rung red. A local climb turns a skip whose reason starts with a mark (`<word>-only:`) red: a task's proof runs every marked test. None known |
| Counts that may not fall | A rung's count (tests passed, or a number captured from its output) is held against its floor in `ratchets`; below it, the rung is red even with every test green, and a count that cannot be read is red too | `ladder[].ratchet`, `ladder[].capture`, `ratchets:` | [BUG-053](../records/bugs.md): a fake program first on the `PATH` can fool a rung |
| New tests must fail on the base | When a count rose, runs the rung on the merge base in a temporary worktree and reports which new tests failed there and which passed (and so prove nothing new) | Automatic; `base_setup` on a rung prepares the base | It reports; it never changes a colour |
| Bless | A green, clean climb on the base branch whose count rose files one ask for a person, `ladder:bless-<task>`, naming each rise | Answer it with `bonsai answer` | Bonsai never writes a floor: blessing "runs nothing"; the floor is raised in `bonsai.yaml` by a person, or an agent under a task granting it |
| The proof file | One `bonsai.ladder/1` result per task in the main checkout's `.bonsai/local/ladder/<task>.json`, wherever the climb ran: the commit climbed, whether the tree was dirty, local or CI, every rung's status, time, tests and counts. Its SHA-256, with the running `bonsai`'s own path and hash, goes to the log | Read it; never write it by hand | The log is plain text nothing signs: a hand-written log record could make a hand-edited result read as an earlier climb's (it steers git integrity's comparisons, never a colour); a chain of fingerprints is not built. [BUG-045](../records/bugs.md) |
| Next step on red | Names the first red rung's fix, with each failing test's own command, then the climb again; a fix that is a `bonsai.yaml` change is marked for a person | In the output; `next` in `--json` | [BUG-087](../records/bugs.md) |
| Settings as committed | Rungs, floor, ratchets and CI marks are read from `bonsai.yaml` as committed at the main checkout's HEAD; an uncommitted change refuses the climb (`config-uncommitted`) | Commit or revert the change | The main checkout must be verified on this machine and on its recorded base branch (`main-not-verified`) |
| Looser settings wait for you | A climb, and the stop gate, refuse committed settings looser than the ones this machine last accepted (`config-looser`), naming each: a rung added, removed or changed, a floor rung or a ratchet taken out, a floor lowered, a CI mark added, a path taken off the protected, person-only or never-edit lists. Stricter settings (a floor raised, a path added) are accepted and recorded by the climb itself | You run `bonsai update` in the main checkout, in a terminal of your own; Bonsai refuses it from an agent's session | A rung added counts as looser because its command runs inside the climb. [BUG-050](../records/bugs.md), [BUG-055](../records/bugs.md), [BUG-026](../records/bugs.md) |
| CI | `--ci` writes `.bonsai/local/ladder/ci.json`, marked `mode: ci`, which is never a task's proof; tests named in `ci_marked_tests` may skip there. The skill `base:ci` is a GitHub Actions workflow that runs `bonsai check` on every push and pull request | `bonsai ladder --ci [--task <id>]`; copy `base:ci` to `.github/workflows/bonsai.yml` | Nothing shipped runs the ladder in CI; a project's own workflow would call `bonsai ladder --ci`. Adding a name to `ci_marked_tests` is a loosening. [BUG-053](../records/bugs.md) |
| Leftover processes | After a local climb, lists processes still running from the checkout that the climb did not start | In the result's `leftovers` | Never changes a colour; not on macOS. [BUG-029](../records/bugs.md): it also lists a session's own tool servers |

## Records

Bonsai's documents and tables have fixed formats that a person and a program read the same way, and `bonsai check`
holds a project to them. Bonsai reads these records and never applies anything from them: it does not move a task.

## Not built, and known limits

**The guard is a tripwire, not a wall.** It stops an agent's accidents and the known ways of cheating, not a
determined agent running as the same user ([the design, section 7](../design/bonsai-spec.md#7-guards-and-walls)). What
catches the rest comes after the fact: rung 0 of the ladder, the result's `dirty` mark, and a person's or a reviewer's
read of the diff. In particular:

- The guard judges file edits and shell lines, not reads, searches, web or MCP calls; reads are stopped only by deny
  rules, and those stop Claude Code's own tools, not a script or a program that reads a file itself.
- It reads a shell line's words and never runs a shell, so a write through an interpreter, a script, a command built in
  a variable or a program's own calls is not seen (the bugs from [BUG-036](../records/bugs.md) to
  [BUG-040](../records/bugs.md)).
- Agents are attributed, not authenticated: a write the guard cannot read could forge an agent's state, a message or a
  log record ([BUG-045](../records/bugs.md)). This machine's record of the checkout, in Bonsai's home, is writable by an
  agent's shell ([BUG-050](../records/bugs.md)).
- It guards Claude Code only, and only a session started in the project's top folder with its hooks on. A person's own
  settings or a mod can turn the hooks off or approve a refused call.
- On Windows, Claude Code's PowerShell tool ignores Read and Edit deny rules.
- Claude Code ends a turn after eight stop-gate blocks in a row.

**What Bonsai does not do, by design.** It applies no action: it never moves a task, applies an approval, lands work or
starts an agent. It has no daemon, no network service, no terminal UI and no screens of its own; dashboards,
notifications and deploys are its users' to build. Nothing in the program applies a landing rule: a project that wants
"land only on a green local result and green CI" writes that rule for its agents.

**Not built.**

- A sandbox: the design names it for after a probe; no code writes or enables one.
- Running the ladder in CI as a task's proof, and a task done only with it green ([BUG-053](../records/bugs.md)); `--ci`
  exists, and `base:ci` runs `bonsai check` only.
- A signed or chained record of ladder results.
- A migration from Bonsai 0.4.3.
- Commands to add or remove a pack, edit `bonsai.yaml`, move a task, search the log by text, or clean generated files
  on demand.
- Filters for `bonsai agents` (planned).
- A pack's needs beyond Claude Code's version: the `mcp` and `shell` kinds are listed but not written by this build.
- A tested macOS build, and an installer for it.
