# base: Bonsai's own pack

`base` is the pack Bonsai publishes for every project it links. It holds:

- **The templates of Bonsai's documents**, as skills: a task, a run report, a memory note and its index, a message
  between agents, STATE, `bonsai.yaml`, and a CI workflow that runs `bonsai check`; and the page on what Bonsai
  generates in a project and how long it keeps each kind. Each loads as `base:<name>` when an agent opens it.
- **The operating skill**, `base:operating-bonsai`: how an agent runs Bonsai unattended, every command read by its
  `--json` and each refusal by its next step, and the steps that stay the person's.
- **The walls**: deny rules that stop agents reading the files that commonly hold keys, tokens and logins, and
  editing the person's own Claude Code files and the files whose change starts code.
- **Bonsai's four labels** (`bonsai.allows`, `bonsai.wants`, `bonsai.ladder`, `bonsai.branch`), whose definitions a
  project needs before `bonsai check` can hold a task's labels to them.
- **Base's protected paths**: `bonsai.yaml` and the lock, `.bonsai/lock.json`.
- **A short block**: a few lines in the project's `CLAUDE.md` naming the skills, so every session knows they exist.

It has no roles, no lanes and no document kinds of its own (Bonsai's kinds are built into Bonsai), and **it carries no
code**: no hook line, no file the engine writes into a project, nothing in the plugin that Claude Code runs on its
own. `packs/packs_test.go`, in Bonsai's repository, fails if any of that changes.

A pack is a Claude Code plugin (here: its skills) plus a `bonsai/` folder, which Bonsai's engine reads when a project
links the pack; Claude Code never reads `bonsai/`. Base lives in Bonsai's repository, in `packs/base/`, and is checked
by Bonsai's CI on every commit: `bonsai check --pack`, `claude plugin validate`, and a scratch project linked to it.

## How a project takes base

`bonsai init` links a project to a pack by its repository, its folder there and a ref (a tag, or a 40-character
commit before base's first release):

```sh
bonsai init --name <project> --source https://github.com/LastStep/Bonsai --path packs/base --ref <tag or commit> --json
```

Without `--yes` that is a preview: it lists every line it would write (the walls among them, each with its sentence)
and writes nothing. Since base runs no code, nothing appears under "Runs code", and `--yes` alone links it; no
`--allow-exec` is needed. Moving base to a newer release is a person's step, as for any pack: change its ref in
`bonsai.yaml`, then run `bonsai update`, whose preview says what changes. Base's releases are tagged `base-vX.Y.Z`
(`bonsai/pack.yaml`'s `version` after `base-v`), never a bare `v` tag, which is Bonsai's own.

## The folder

| File | What it is |
|---|---|
| `.claude-plugin/plugin.json` | The plugin manifest Claude Code reads; documented below, under "plugin.json" |
| `bonsai/pack.yaml` | Base's Bonsai manifest (format `bonsai.pack/1`): its id and version, the Claude Code it needs, its block, the walls and its protected paths. A `#` comment on every key |
| `bonsai/labels.yaml` | Bonsai's four labels (format `bonsai.labels/1`), as contract section 5.6 defines them. A `#` comment on every key |
| `bonsai/block.md` | Base's part of the block in a project's `CLAUDE.md`; its leading HTML comment documents it and stays in the pack |
| `skills/` | The skills, one folder each holding its `SKILL.md` and nothing else (no script a skill could run) |
| `README.md` | This page |

Its files are LF on every checkout, through the `packs/**` line of the repository's `.gitattributes`.

## Skill files

Each file in `skills/` has its row here, and each row names a file there (Bonsai's CI checks both ways).

| File | What it is |
|---|---|
| `skills/task/SKILL.md` | `base:task`, a template: a task (`bonsai.task/1`), its fields table with Bonsai's four labels, and the template to copy |
| `skills/run/SKILL.md` | `base:run`, a template: a run report (`bonsai.run/1`), the log of one session on one task |
| `skills/memory/SKILL.md` | `base:memory`, a template: a memory note (`bonsai.memory/1`), its index line and the budgets |
| `skills/message/SKILL.md` | `base:message`, a template: a brief or a report between agents (`bonsai.message/1`), each written with `bonsai message` |
| `skills/state/SKILL.md` | `base:state`, a template: STATE (`bonsai.state/1`), the page that says where a project stands. Generated from Bonsai's code by `go generate`; never edited by hand |
| `skills/workspace/SKILL.md` | `base:workspace`, a template: `bonsai.yaml` (`bonsai.workspace/1`), the project's Bonsai settings. Generated by `go generate`; never edited by hand |
| `skills/generated-files/SKILL.md` | `base:generated-files`: what Bonsai and its agents generate in a project, how long each kind is kept, and what is never cleaned. Generated by `go generate`; never edited by hand |
| `skills/ci/SKILL.md` | `base:ci`: a GitHub Actions workflow a project copies to `.github/workflows/bonsai.yml`, running `bonsai check` with no pack fetched; every key commented |
| `skills/operating-bonsai/SKILL.md` | `base:operating-bonsai`: how an agent runs Bonsai unattended, every command by its `--json` and each refusal by its next step: link, update, check, status, `bonsai.yaml`, the ladder, asks, briefs and reports, budgets, the guard and the person's gates. No template; Bonsai's `cmd/bonsai/operating_test.go` holds every `bonsai` line in it to the command table |

### How each kind of file documents itself

- **A template skill** (task, run, memory, message, state, workspace): a fields table, `| Field | Meaning | Allowed
  values | Example |`, above its template, the first fenced block after the table. `bonsai check --pack` holds the
  table and the template's fields equal, both ways, and, for a Bonsai format, equal to the format's schema, with each
  allowed-values cell that lists values equal to the schema's list. A file made from a template keeps only the
  pointer comment on its `format:` line (`# fields: bonsai check --schema bonsai.task; how to fill: skill base:task`).
- **A skill that is no template** (generated-files, ci, operating-bonsai): an HTML comment after the frontmatter, or the generator's
  note, saying what it is and where its fields are documented.
- **A YAML file** (`pack.yaml`, `labels.yaml`): a short header, and a `#` comment on every key.
- **`block.md`**: its leading HTML comment. **`plugin.json`**: this page.

### Skill files: frontmatter fields

| Field | Meaning | Allowed values | Example |
|---|---|---|---|
| `name` | The skill's name; the folder is `skills/<name>/`, and the skill loads as `base:<name>` | a lower-case letter, then lower-case letters, digits and dashes | `task` |
| `description` | What the skill holds and when to open it: Claude reads it to decide whether to load the skill | one line of text, quoted | `"The task template (bonsai.task/1): ..."` |

## plugin.json

| Field | Meaning | Allowed values | Example |
|---|---|---|---|
| `name` | The plugin's name, which Claude Code puts before every skill (`base:task`) | the pack's id, exactly as `bonsai/pack.yaml`'s `id` | `"base"` |
| `description` | What the pack is, in a sentence, as Claude Code's plugin lists show it | text | `"Bonsai's own pack: ..."` |
| `author` | Who makes the pack | an object; `name` is the maker's name | `{"name": "Bonsai"}` |
| `repository` | Where the pack's source lives | the repository's address | `"https://github.com/LastStep/Bonsai"` |

**It never carries `version`:** a project pins base by commit, and that commit is the version Claude Code sees; with a
`version`, Claude Code would keep each machine on its cached copy whatever the commit. `claude plugin validate --json`
warns about the missing `version`, the one warning Bonsai's CI allows. No hooks, MCP or LSP servers, monitors or other
component folders are named here: base carries no code.

## The walls

**Where they live:** `bonsai/pack.yaml`'s `deny` list, their one home, each rule with its `why`, the sentence `bonsai
update`'s preview prints after `base: `. The engine writes them into each linked project's `.claude/settings.json`,
after Bonsai's own rules. This page says what they are for and what they leave out; it never copies the list.

**What is walled, one rule for all.** Read: the files and folders that commonly hold keys, tokens or logins (SSH,
GnuPG, cloud command lines, git's stored logins, package registries, Docker, Kubernetes, Claude Code's login and its
own file, other AI and ML tools' logins (OpenAI's Codex, Gemini's command line, Hugging Face, CLIProxyAPI, the pi
coding agent), Bonsai's salt). Edit: the person's own Claude Code files (their settings, their local settings in any
folder, their memory file, Claude Code's own file whose MCP servers it starts), and the files whose change starts code
(a folder where a copy could shadow the installed `bonsai`, SSH's settings, git's settings, the shells' start files,
PowerShell's profiles). An Edit rule also stops a Write and a shell redirect into the file. A rule names an exact file
where one is enough, and a folder only where a tool keeps several; base is public and serves projects on any machine,
so this rule, not one machine's listing, decides what is in.

**Each wall has its twins.** `~/` is the session's own home: on Windows, the Windows home. A session in WSL reaches the
Windows home as `//mnt/c/Users/*/`, and a session on Windows reaches WSL's home by its network paths,
`//wsl.localhost/*/home/*/` and `//wsl$/*/home/*/`. So each wall is written for each home where a common program keeps
that file. A twin is left out only where none does (each group in `pack.yaml` says which): a Windows tool's own place
under `AppData/` or `Documents/` has no twin in WSL's home, and the Windows home has no twin for a file its tools keep
elsewhere (gh's and Google Cloud's logins live under `AppData/` there) or for zsh's start files, which no common
Windows shell reads.

**Bonsai's own rules are not base's.** The rule over `.bonsai/local/` (the log, asks and ladder results), the rules
over the two generated tables, and the rule over Bonsai's home, `~/.bonsai/`, are the engine's own: it writes them into
every linked project whatever its packs, and base never repeats one. Base keeps the Read wall on Bonsai's salt,
`~/.bonsai/salt`, a secret's wall.

**What the walls do not do.** They are deny rules, a tripwire against accidents, not a wall against a determined
program. A Read rule stops Claude Code's file tools and `cat`, `head` and `tail` on that path; it does not stop a
script or a program that reads the file itself (`ssh`, `gh` and Claude Code still read their own files). They bind
only the projects linked to base, and only the sessions in them; a person's own Claude Code settings can widen a
session past them, and a mod can approve a call they would refuse. Narrow rules are kept narrow on purpose, so the
sandbox, where it is used, stays small: each folder rule is a recursive glob, which the sandbox turns into one rule per
file in that folder.

**What holds where, as tried on both sides** (16 Oct 2026, Claude Code 2.1.301, each rule form over decoy files).
In WSL every wall held: the Read, Edit and Write tools, `cat`, `head`, `tail` and a shell redirect were all refused.
On Windows the walls hold for the Read, Edit and Write tools in every form, and for Git Bash on `~/` paths. Two things
they do not stop there, because Claude Code's deny rules do not reach them, and no rule form was found that does:

- **The PowerShell tool ignores Read and Edit deny rules entirely.** `Get-Content` read a walled file and
  `Add-Content` changed one, on every form, `~/` included. A person on Windows who does not need the PowerShell tool
  can take it away in their own Claude Code settings with a deny rule on the tool's name,
  `"permissions": {"deny": ["PowerShell"]}` (Claude Code's form for a whole tool; not part of these tries). Base does
  not, since a pack cannot know which projects need the tool.
- **Git Bash passes the WSL home's network paths.** `cat "//wsl.localhost/<distro>/home/<user>/..."` read a walled
  file and a redirect `>>` changed one, the same with `//wsl$/`; the file tools on the same path refuse. Eight rule
  spellings were tried (a single, double and triple leading slash, a backslash path, `**` in place of the distro and
  user, the literal distro and user, and a bare `**/` tail): none stopped the shell; Claude Code does not seem to
  match a network path in a shell command against these rules. So a native Windows session can read WSL's key files through
  Git Bash by that path, and the walls do not stop it. The `//wsl.localhost/` and `//wsl$/` twins are kept for the
  file tools, which they hold.

**Places left out, and why:**

- **A Documents folder moved elsewhere** (a sync tool's known-folder move, `~/OneDrive/Documents/`, say): the
  PowerShell walls name `~/Documents/`, which does not reach the moved folder. A project on such a machine adds the
  moved folder's rules in a pack of its own.
- **Windows homes on another drive than `C:`, or WSL mounting drives under another root than `/mnt/`**: the
  `//mnt/c/Users/*/` twins name the usual place only.
- **A WSL user whose home is `/root/`**: the WSL-home twins name `home/*/`, every user but root.
- **Other shells' start files and the rarer ones of bash and zsh** (`.bash_login`, `.bash_logout`, `.zshenv`,
  `.zlogin`, `.zlogout`, fish's and PowerShell's on Linux under `~/.config/`): base walls the start files bash and
  zsh read in their usual setups (`.bashrc`, `.bash_profile`, `.profile`, `.zshrc`, `.zprofile`); a project whose
  people use another shell, or those files, adds their rules in a pack of its own.
- **Files a project keeps its own secrets in** (a `.env`, a key in the repository): they are the project's, not the
  machine's; a project walls them with `never_edit` in `bonsai.yaml` or a deny rule in its own pack.

## The labels, the protected paths and the block

- **Labels:** `bonsai/labels.yaml` defines `bonsai.allows` (the protected paths a task may change; the only label
  that grants a right), `bonsai.wants` (the person-only paths a task asks for), `bonsai.ladder` (the rungs a task
  climbs beyond the floor) and `bonsai.branch` (the branch it is built on). They are contract section 5.6's, field
  for field, which `packs/packs_test.go` holds. The engine copies them into a project's lock, and the block in
  `CLAUDE.md` shows agents each one's description.
- **Protected paths:** `bonsai/pack.yaml`'s `protected` lists `bonsai.yaml` and `.bonsai/lock.json`: an agent changes
  them only while its running task grants them in `bonsai.allows` (and, as each project's `person_only` list says,
  only when a person granted them).
- **The block:** `bonsai/block.md`'s lines, after its leading comment, go into the block in a linked project's
  `CLAUDE.md`, which loads in every session; they name base's skills and stay at most four lines.

## Checks

From the top of Bonsai's repository, with a `bonsai` built from it:

- `bonsai check --pack packs/base --json`: the manifest, the labels, every key's comment, every deny rule's `why`, the
  block's size, `plugin.json` without `version`, and each template skill's fields against its format's schema.
- `sh packs/template/ci/check.sh validate packs/base`: `claude plugin validate --json`, failing on every warning but
  the missing `version`; it needs no Claude login.
- `sh packs/template/ci/check.sh check <bonsai> packs/base . <commit> packs/base`: the two above, this page's skill
  rows, and a scratch project linked to base at that commit with `--yes`, then `bonsai check` there.
- `go test ./packs/`: base stays free of code (`hooks: []`, `files: []`, no plugin part that runs, each skill folder
  its `SKILL.md` alone), its labels stay contract section 5.6's, and no engine rule is repeated among the walls.
