# Plan: Bonsai's first existing project, the ZenGarden-AI-API pilot

Two readers. **The director** reads the first part only (down to Size). The **builder and verifier** read the rest.

## For the director (plain words)

**What this will do.** ZenGarden-AI-API gets Bonsai the way LinkSink did, but as a project with history:
1. An agent rehearses the whole link on a throwaway copy of the project. That covers both packs, the `.env` files
   walled off, and one proof step that runs the 305 tests, climbed green. The rehearsal finds the problems before
   anything touches the real project.
2. You run one script in the real project: it previews, then links. You open Claude Code there once to accept the
   plugins.
3. You then start Claude Code in that project with a kickoff note we give you. Its own orchestrator, under its own
   tasks:
   - sorts the old agent system into four groups (the director, 26 Oct, "A, rest looks right"):
     - what Bonsai replaces is archived unchanged;
     - the still-useful guides are kept in `docs/guides/`, brought up to date and linked from CLAUDE.md;
     - lasting facts become memory notes;
     - history is archived;
   - trims CLAUDE.md to the project's facts (hardware limits, architecture, how to run it);
   - writes its STATE;
   - takes one real fix through the full builder, ladder and landing loop. The suggested fix: CI should not push an
     image when the tests are red.
4. Back here, two agents read what happened, and a trial record says what worked and what didn't, with every Bonsai
   bug found filed. ZEN comes after, on what the pilot teaches.

**Choices that are yours.** None now; you answered them ("A, AI-API first"). The project's own orchestrator will
ask you which real fix to run through it.

**Risk.**
- **Production deploys.** The project deploys to production on every push to its `main`, so nothing from the pilot
  is pushed to GitHub without your word. Its work lands on the local `main` only.
- **A blocking Bonsai bug.** If the rehearsal or the link hits a Bonsai bug that blocks the work, the pilot stops and
  reports. Bonsai's code is not patched inside this task.
- **Rough edges to expect:**
  - Claude Code may say "Unknown skill" until it restarts (BUG-107).
  - The workflow pack's game-studio wording ("a player").

**Size.**
- Rehearsal: about 1 hour of agent time.
- Your part: about 20 minutes (one script, one Claude Code open and quit, the kickoff).
- The project's sessions: 2 to 3 hours, with you there for its questions.
- The trial record: about 1 hour.
- Nothing needs setting up first. The project's tests need no service.

### Approach

**1. Rehearsal and the script.** A `workflow:builder` (sonnet), scratch only.
- **Its working folders:** `~/bonsai-checks/T-6001/` and `~/bonsai-checks/scripts/T-6001/`, with no edit to
  Bonsai's repo or to the real project.
- **The copy:** `git clone ~/ZenGarden/ZenGarden-AI-API ~/bonsai-checks/T-6001/rehearsal`, then
  `git remote remove origin` in it (the clone's origin is the real project). Then a fresh venv made from
  `requirements-test.txt`, as CI does, and its pytest count read: **the ratchet is that count**, not the 305 read
  with the project's drifted venv. A different count is reported, not hidden.
- **A `.ruff_cache/` made in the copy** (`ruff check --cache-dir` default, or `mkdir .ruff_cache && printf '*\n' >
  .ruff_cache/.gitignore`, as ruff makes it), because the real project has one and a fresh clone does not (review
  B3). The rehearsal shows git integrity reads it dirty before the fix and clean after.
- **A scratch home:** a `BONSAI_HOME` under `~/bonsai-checks/T-6001/home`.
- **A stamped build for every rehearsal command** (review B1). The installed `bonsai` refuses `update` that adds
  rungs from an agent's shell (a loosening, a person's step), and only a stamped build's scratch root lets an agent
  run it. The builder builds the 1.0 commit `48d5f3f0` in a scratch clone of Bonsai, as earlier scratch scripts do:
  ```
  go build -buildvcs=true -ldflags "-X github.com/LastStep/Bonsai/internal/engine.hookPlace=$B \
    -X github.com/LastStep/Bonsai/internal/engine.scratchRoot=$HOME/bonsai-checks/T-6001" -o "$B" ./cmd/bonsai
  ```
  with `B=~/bonsai-checks/T-6001/bin/bonsai`, never `go install`. `link.sh` takes the binary from `BONSAI_BIN`,
  default `/usr/local/bin/bonsai`. **What this leaves unproved:** the real link runs the installed 1.0, whose
  code is the same commit but unstamped; its hook lines name `/usr/local/bin/bonsai`, which the rehearsal's do not.
  The director's run is the first proof of those.
- **`link.sh`:** the builder writes `~/bonsai-checks/scripts/T-6001/link.sh <checkout> [--yes]`. With no `--yes` it
  only previews.
  - **It runs `bonsai init`:**
    ```
    bonsai init --name zengarden-ai-api --source https://github.com/LastStep/Bonsai.git --path packs/base \
      --ref base-v1.0.0 --never-edit .env --never-edit .env.local --never-edit .env.production
    ```
  - **It adds the workflow pack** (`source: https://github.com/LastStep/bonsai-workflow.git`, `path: null`,
    `ref: v1.0.0`, `roles: null`) to `packs:`.
  - **It adds the ladder:**
    - `ladder_floor: [0, 1, 2]`;
    - rung 0 `guard`;
    - rung 1 `ver-git`;
    - rung 2 the tests: `.venv/bin/python -m pytest -q -p no:cacheprovider tests/`, `timeout_s: 300`,
      `ratchet: tests`, `tests: null`, `base_setup: null` (it runs only when new tests are checked at the merge
      base, and only on a rung with a tests form, so it makes no worktree's venv), and the capture;
    - every mapping in **block form**, never braces on one line, which Bonsai refuses in `bonsai.yaml` (review B2;
      base:workspace, "Mappings"):
      ```yaml
          capture:
            tests: "([0-9]+) passed"
      ratchets:
        tests: <the fresh venv's count>
      ```
  - **It adds `.ruff_cache/` to the committed `.gitignore`** (B3), so the first climb in the real project is clean.
  - **It runs `bonsai update`, then `bonsai check`,** and commits `link Bonsai`. That `update` records the ladder;
    in the director's terminal it is a person's, so no second `update` is needed after.
  - **Every edit to `bonsai.yaml`** is an exact, idempotent text change, checked by `bonsai check` after.
  - **Scratch runs:** in the rehearsal it runs through the script with the scratch home, the way Bonsai's CLAUDE.md
    says scratch links run from a guarded session.
- **The spike.** In the rehearsal, try the tests read as JUnit on stdout (`--junitxml=/dev/stdout`, `tests: junit`),
  which names each failing test, against capture-only:
  - keep JUnit only if Bonsai reads it whole and the count equals the capture's;
  - with JUnit, `base_setup` must make the base worktree's venv (pip from `requirements-test.txt`), and the time
    that adds at each rise in the count is measured against the rung's 300 s;
  - otherwise capture-only stays, `base_setup: null`.
- **The rehearsal proves:**
  - `bonsai check` and `bonsai status` report no finding and nothing changed or missing;
  - CLAUDE.md is kept byte for byte outside Bonsai's block (diff against the original);
  - `.env*` edits are refused by the guard: a probe Write in a scratch Claude Code session is the runner's job, and
    a `bonsai check` of the deny rules is enough here;
  - a climb on the rehearsal's main is green and clean (`git.dirty` false, `.ruff_cache/` present), rung 2 at the
    ratchet: `bonsai ladder --task T-0001` with a scratch `work/tasks/T-0001` reading `running` and granting
    nothing, **committed before the climb** (an untracked file reads `git.dirty` true);
  - a climb in a worktree of it, at `~/bonsai-checks/T-6001/rehearsal-wt` (inside the stamped build's scratch
    root, which refuses a climb outside it), branched from `main` after the link commit (BUG-047), is green once
    its venv is made; that recipe goes in the kickoff.
- **Clean-up after the rehearsal:** the scratch workspace's plugins under `~/.claude/plugins` and its marketplace
  entry are removed (BUG-107), and every process the builder started is stopped; both said in its report.
- **The builder also writes `~/bonsai-checks/T-6001/kickoff.md`.** This is the first prompt for the project's
  orchestrator. It covers:
  - the director's decision A (retire the old system, keep it read-only);

### Choices made, and what lost

| Choice | Alternative | Why this one |
|---|---|---|
| Rehearse on a clone first | Link the real project straight away | First existing project; a surprise costs nothing on a clone |
| The link and ladder in one script the director runs | The director edits `bonsai.yaml` by hand (LinkSink) | The director writes no code; one rehearsed, reviewed script; fewer person steps |
| Tests counted by `capture` | JUnit on stdout | pytest prints no TAP or JSON of its own; JUnit is kept only if the spike proves Bonsai reads it whole |
| ruff and mypy left out of the ladder | Rungs with ratchets | A ratchet holds a count from falling; it cannot hold an error count from rising. They join once clean, by the project's own task |
| The venv per checkout, from `requirements-test.txt` | One shared venv by an absolute path | A path in `bonsai.yaml` would name a home folder; the CI set is what is proved today |
| The old system sorted: replaced parts and history archived unchanged, guides kept | Everything archived, or deleted | The director's A: history kept read-only, and the still-useful guides stay in use |
| Guides as plain files in `docs/guides/` | Claude Code skills in `.claude/skills/` | The director, 26 Oct ("A"): `.claude/**` is person-only in a linked project, so every guide fix would need the director's grant |
| Work lands on local `main` only | Pushed | Every push to `main` deploys to production |

### Risk in the code

- **The script edits `bonsai.yaml` as text.** A wrong edit could leave the file unread (init's exit 2) or looser
  than meant. Mitigations:
  - it is rehearsed;
  - it is idempotent;
  - `bonsai check` runs after each edit;
  - the security verifier reads it.
  - Fallback: the director edits as for LinkSink.
- **A climb could read dirty for another untracked file** the real project has and a clone does not. Before the
  director's run, the builder's report lists `git ls-files --others --ignored --directory --exclude-standard` of the
  real project (read-only) and says which each is (the review's run found only `.ruff_cache/` outside the root
  `.gitignore`). The test suite left the tree clean in two runs (`test_logs` never made).
- **Stop and report `blocked`:**
  - on any Bonsai refusal whose `next.who` is not `person` and that the docs do not explain;
  - on any need to patch Bonsai;
  - on any step that would push the project.
