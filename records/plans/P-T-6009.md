# Plan: a pack command (add, remove and move a project's packs, and see which are behind)

Two readers. **The director** reads the first part only (down to Size) and reads no code: it is in plain words. The
**builder and verifier** read the rest, and it may carry code where it helps: paths, signatures, short snippets, exact
commands. The director writes, reviews and verifies no code, so the agents own it end to end.

## For the director (plain words)

**What this will do.** Bonsai gets a new command, `bonsai pack`, so moving a project to a newer pack is one command
instead of a hand edit and an update:

- `bonsai pack outdated` lists each pack with its current version and the newest one, asking GitHub. Safe for anyone,
  agents included.
- `bonsai pack set base@base-v1.0.1` moves a pack to another version. `bonsai pack add` links a new pack, and
  `bonsai pack remove` takes one out. Each shows one preview: the `bonsai.yaml` line, every file, setting and plugin
  that changes. Then `--yes` writes it in one go; if anything fails before the write (a fetch, a check), nothing is
  written. Only the version text on the line changes; your comment on it stays as it is.
- Plain `bonsai status` (and the studio's screen through `--json`) shows each pack's version and, from a cache, whether
  a newer one exists and when that was last checked. It still never touches the network. The cache refreshes whenever
  you run `pack outdated` or `status --full`. Bonsai's own "newer release" line is fixed too: it no longer calls 1.0.1
  "current" against a stale 1.0.0; it says it doesn't know, and names `bonsai status --full` (BUG-139).

Who may apply, by your answers of 28 Oct:
- An agent may apply a pack change after your yes, under a task that grants `bonsai.yaml` and the lock, as with
  `bonsai update` today.
- A change that removes protections is yours alone: a `pack remove`, or a move whose new version drops deny rules
  or protected paths. The preview lists each protection that goes, and `--yes` refuses in an agent's session, whatever
  it was granted. The same now holds for plain `bonsai update`: an agent can no longer drop a pack by editing
  `bonsai.yaml` by hand and updating (the plan review found that way round; this closes it).

**And eight more, your picks of 28 Oct** ("check and see if we can build something more into this new feature"; all
eight taken), built as a second stage once the core has landed:

1. **What changed:** `pack set`'s preview lists the pack's changes between your version and the new one (its commit
   titles), and `pack outdated --changes` does the same for every pack that is behind.
2. **A session nudge:** a Claude Code session's opening context names the packs that are behind, from the cache, with
   no network.
3. **Update all:** `bonsai pack set --all` moves every pack to its newest tag in one preview and one `--yes`.
4. **A downgrade guard:** a move to an older tag needs `--downgrade`.
5. **A compatibility check:** a version that needs a newer Claude Code than this machine has, or a pack format this
   Bonsai cannot read, is refused before anything is written. This changes your 7 Oct rule ("warn only, never
   refuse"), by your word of 28 Oct ("Refuse, change the rule"): the spec's line is rewritten with it.
6. **A hint for the old plugin registration (BUG-107, in part):** after a move, Bonsai names the old plugin
   marketplace still registered on this machine and the exact command to remove it, to run once no other checkout
   uses it. Nothing is removed for you (your word of 28 Oct: "Hint, don't remove"); Bonsai already clears the old
   install records itself.
7. **Commit lines:** after `--yes`, the exact commands to commit the files written, one per line (so they work in
   PowerShell too).
8. **Pack details:** `bonsai pack show <pack>`: its version, skills, roles, protections and needs.

**And three from the studio, your yes of 28 Oct, in stage 1** (so the studio's screen, which reads `--json` only,
gets them with the core):

- The `--json` preview carries the `bonsai.yaml` line (before, after, its kept comment) and the list of protections a
  change removes, not only the text preview.
- `pack outdated --json` prints a named format of its own, with its schema, as every `--json` output has.
- A preview and its apply are tied: the `--json` preview carries a fingerprint of the planned changes, and
  `--yes --expect <fingerprint>` writes nothing (and says so) if the plan built now differs from the one you read: if
  anything the preview showed would now come out differently. For `bonsai pack` and `bonsai update` alike.

**Choices that are yours.** None left: your six answers, eight picks and the studio's three of 28 Oct are the design
(the run report quotes each). The consequence to know: four protected texts change to match, and this plan's approval
is your word for those edits: the spec's "fifteen command words" line (section 4), the spec's "warn only, never
refuse" line on a pack's Claude Code need (section 7, by your pick 5), and the contract's status section (12) and its
words on the update preview's format.

**Risk.** The delicate part is editing `bonsai.yaml` without a general YAML library while keeping every comment and
every byte it does not mean to change. Every edit is re-read and checked before anything is written, and tests hold
"nothing else changed" for every shape this repo's own file has. If adding or removing a whole pack entry cannot be
made byte-safe, the builder stops and reports. Then `add` and `remove` wait, and `set` and `outdated` ship alone,
which already covers moving the studio and ZenGarden-AI-API. A fresh Opus verifier checks it, because it touches the
guard and person-only paths.

**Size.** Two stages, each landed on its own: stage 1, the core and the studio's three, about 10-15 hours; stage 2,
your eight picks, about 6-9 hours; one Opus builder each, an Opus verifier and CI for each. About 16-24 hours in all,
over two or three sessions. Nothing for you to set up.
It goes out in Bonsai 1.0.2, with base's skill text updated in base 1.0.2. Bonsai's own hook lines do not change, so
no `--allow-exec` step is needed from you.

### Approach

1. **The editor (B).** `internal/engine/configedit.go`: three byte-preserving edits on the raw `bonsai.yaml` bytes,
   each returning new bytes that are re-read with `workspace.ReadConfigFull` and checked to hold exactly the intended
   change:
   - `SetRef(raw, id, ref)`: the `replaceID` pattern (config.go:267-295) on the pack entry's `ref:` line (`Entry("ref").Line`):
     the value's text, searched only after the `ref:` key (a short ref such as `f` must not match the key), replaced,
     quoting as written, its trailing comment kept byte for byte.
   - `AddPack(raw, entry)`: appends one entry at the end of `packs:`, written in init's form with its comments
     (`ConfigYAMLPacks`' per-key comments), indented as the file's existing entries are.
   - `RemovePack(raw, id)`: removes the entry's lines from its first line to the line before the next entry or the next
     top-level key, the bound found from the reader's start lines plus indentation. Comment lines belonging to the next
     entry stay with it.
   Line endings kept as the file has them (CRLF files stay CRLF; fingerprints read LF).
2. **The seam (B).** `engine.Request` gains `Config []byte` (plan.go:80-92). When set, `Build` uses it in place of the
   disk read (plan.go:305), and `bonsai.yaml` enters the plan as an Updated file with its old bytes, as `--new-id` does
   (plan.go:584-586). `Apply` writes it first and the lock last, all or nothing, unchanged.
3. **Loosening (B).** `engine.PackLoosening(oldLock, plan) []string`: every deny rule (the walls are the packs' deny
   rules) and declared protected path the locked packs had that the planned packs do not. A `remove` always loosens
   (named as the pack's removal, with its list); a `set` or `add` loosens when the list is not empty. Packs stay out of
   `workspace/checks.go`'s compared settings (:47-50): this is judged in `runEngine` (cmd/bonsai/engine.go, after
   `engine.Build`, :147), **for every word that applies a plan: `update` as well as `pack`**, so a hand edit of
   bonsai.yaml followed by `update --yes` meets the same gate. A loosening plan's `--yes` is refused by `personOnly`
   (agent.go:91-127), which no grant opens, never `personCommand` (agent.go:60-75, which a grant of bonsai.yaml and the
   lock opens). The preview with no `--yes` lists the loosening for anyone and is never refused for it (unlike
   `ChecksLooser`'s refusal at engine.go:198-203, which refuses a preview too: the new gate refuses only on `--yes`).
4. **The cache (A).** `home/cache/packs.json`, one record per pack source (`git ls-remote` returns all of a source's
   tags; `NewerTags`' prefix rules, newer.go:59-94, are applied at read time): the tags read, `read`, `failed`. Written
   atomically (`workspace.WriteFileAtomic`) by `pack outdated` and `status --full`, which both read live as `--full` does
   today (30 s, `PackTagsTimeout`) and then write the record. Plain `status` only loads it, never reads a source. The
   verdict is computed at read time against the lock's current version, never stored. `newer.tag` is the newest tag
   the record holds by `NewerTags`' rules, or the locked ref itself when none is newer (state `current`; a commit hash for a pack locked to a commit, which the schema's description says); a record
   whose last read failed with no earlier good read is left out (`newer` null), one with an earlier good read keeps it,
   its `read` the good read's time.
5. **The status format (A).** `status --json`'s `packs[]` items gain `ref` and `newer`, added **at the end of the
   items' properties and both added to `required`** (the schema-compare rule, formats/compare_test.go:255-275: a property
   added at the end and required passes; an enum grown is refused). `newer` is `{tag, read, state}` or null when no
   record exists; its `state` (a new enum, not a grown one) is `newer`, `current` or `stale` (the record older than 7
   days, or its newest below the locked version). A new formats set, 13: the set's number raised, `schemaBase` in
   compare_test.go:32 moved to the commit of set 12, `formats/schemas/status.schema.json`, its example and
   `formats/manifest.json` together (CLAUDE.md: `formats/` changes only with its manifest); contract section 12's words
   to match.
6. **BUG-139 (A).** `ReleaseRead.State` (release.go:265-298): a record whose `newest` is below the installed version
   reads `unknown` (the enum is `current`, `newer`, `unknown`, `not-a-release` and may not grow), its `why` saying the
   record names an older release than this bonsai, read on its day, and its next step `bonsai status --full`; never
   `current`. Shown failing on the old code first.
7. **The word (C).** `cmd/bonsai/pack.go`, a registered `*Word` (word.go:96) with four subcommands:
   - `pack outdated [--json]`: per locked pack, its ref, the newest tag, the state; it reads the network (30 s,
     `PackTagsTimeout`), writes the cache, and exits 0 whatever is newer (a refusal only for bad arguments or no lock).
   - `pack set <id>@<ref> [--yes] [--json]`, `pack add --source <url> [--path <folder>] --ref <ref> [--yes] [--json]`
     (the pack's id read from its `pack.yaml`), `pack remove <id> [--yes] [--json]`: each builds the edited bytes (step 1),
     runs the update path with `Request.Config` (step 2), prints update's preview (`bonsai.changes/1`, with the
     `bonsai.yaml` line and its kept comment shown, and the loosening list), and applies on `--yes`. `--keep`, `--adopt`
     and `--allow-exec` pass through as on `update`. The existing gates hold unchanged: Bonsai's own guard line changed
     (a first role pack) is a person's command; code needs `--allow-exec`; a moved tag is refused.
   - Who may apply, at the guard (internal/guard/commands.go): `ownWrites` (:55-62) is a list of whole words, so
     `pack` is judged per subcommand, not added there whole: `pack outdated`, and any `pack` line with no `--yes`, pass
     for every role, including the roles that write nothing (`preview()`, :188-193, extended from init and update to
     `pack`'s previews); `pack set --yes` and `pack add --yes` are judged as an edit of `bonsai.yaml` and the lock, as
     `update` is (:163-171), so a grant opens them (decision 2); `pack remove --yes` is refused `person-command` with
     no grant opening it, from a new list beside `ownHome` (whose `home-command` and its sentence are the wrong word
     here), and `delHoldsBonsai` (shell_words.go:2017) gains it. A fed line must not slip past: `ownOpen`
     (commands.go:85-103, asked by `delFedBonsai`, shell_words.go:516-528) treats `pack set`, `pack add`, `pack remove`
     and `pack` with no subcommand as open, as it treats init and update, so xargs appending `--yes` is judged as the
     written form. At the command (cmd/bonsai): `remove --yes` refused by
     `personOnly`; a loosening `set` or `add` refused by step 3's gate, its next step the exact line for the person.
7b. **The preview's `--json` and the fingerprint (C, the studio's three).** All the formats change once, in stage 1,
   so set 13 lands in one commit series (stage 2 then fills fields stage 1 defines, with no format change of its own):
   - `bonsai.changes/1` (update's and `pack`'s output) gains, **at the end and each added to `required`**: `config`
     (the bonsai.yaml edit: path, line number, before, after, the kept comment; null when the file is not edited),
     `loosening` (each protection a plan removes: its kind, deny rule or protected path, its value and its pack; `[]`
     for none), BUG-017's two (update's memory lines and its cache-clean line, in the shapes the text preview prints
     them), `pack_changes` (stage 2's commit titles per pack; `[]` until then), `commit_lines` (stage 2's; `[]` until
     then), `fingerprint`, and `word` (`{name, sub}`: `{"update", null}` for update, `{"pack", "set"}` and so on). The
     schema's `command` enum (`init`, `update`, `unlink`) may not grow, so a `pack` apply prints `command: "update"`
     (it is an update with an edited bonsai.yaml) and names itself in `word`.
   - `bonsai.packs/1`, a new format, for `pack outdated --json` now and `pack show --json` in stage 2: every field
     both print (source, path, ref, commit, version, needs, skills, roles, deny rules, protected paths, kinds, the
     cache's newer record), defined now; stage 1's `pack outdated --json` fills them offline: every field from the lock
     but `skills`, which the lock does not hold (internal/workspace/lock.go:55-65, format/declares.go:40-52); `skills`
     is read from the home's pack clone at the locked commit (never cleaned while the lock names it) and is null when
     that clone is missing, so the schema lets it be null. No field waits on stage 2.
   - The fingerprint: SHA-256 of the plan's own fields only, canonical (keys in the schema's order, lists in the plan's
     order, byte-stable, no map order, the same on Windows): the workspace, each planned file (path, action, the old
     and new fingerprints), each planned settings line, each pack's planned ref and commit, `config`, `loosening` and
     `pack_changes`, and `command` and `word` (so a fingerprint from a `pack set` preview is refused by `update --expect`
     and the reverse: the person applies what they previewed, by the same word). Left out, as outcome or flag fields
     that differ between a preview and its `--yes` run: `result`, `error`, `allow_exec`, `plugins`, BUG-017's memory
     and cache lines, `commit_lines`, any read time, and `fingerprint` itself. The files' fingerprints are hashed from
     the plan though `--json` does not print them. The builder lists the two sets in the schema's description of
     `fingerprint`. `--expect <fingerprint>` on `update`, `pack set`, `pack add`, `pack remove` with `--yes`: Bonsai builds
     the plan again and, when its fingerprint differs, writes nothing and refuses `plan-changed` (a new error word,
     exit 4, its next step: read the preview again). Without `--expect`, as today. `--expect` opens no gate.

### Risk in the code

- **Remove's end bound** is the most likely failure: an entry followed by a comment block, by a top-level key with no
  blank line, or the last entry of the file. If a test shows a byte outside the entry changing, stop and report
  blocked; `add` and `remove` are cut from this task, and `set`, `outdated` and the cache land alone.
- **Agents' gates:** the guard cannot tell a loosening `set` before the command runs (the plan is needed), so the
  command layer's `personOnly` refusal in `runEngine` is the gate, for `update` and `pack` alike. The verifier checks
  that no path lets an agent's `--yes` apply a loosening plan, a grant or not: `pack`, `update`, `init` on a linked
  project, and a fed or wrapped `bonsai` line.
- **The network in tests:** no test reaches the network; `RemoteTags` is faked as the existing `--full` tests do.
- **Word count:** the registry's order numbers and the help schema; the words test (`operating_test.go`) must list `pack`.
- **Out of this task:** `unlink` removes every pack's protections and a grant still opens it for an agent (existing
  policy, noted by the plan review; filed for the director, not changed here).
