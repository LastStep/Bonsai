# Plan: bugs as Bonsai's own documents, with commands

Two readers. **The director** reads the first part only (down to Size). The **builder and verifier** read the rest.
The choices behind it are in `records/options/OPT-0003-bug-rows.md` (the director, 19 Nov), its notes and verdicts.
Revised after the plan reviews `M-2026-11-19-510b2fff` (4 blocking findings, 9 notes) and `M-2026-11-19-9631823a`
(2 more), each answered below.

## For the director (plain words)

**What this will do.** Each bug becomes its own small file (`records/bugs/BUG-145.md`), the way tasks are, in a
format Bonsai owns. The one page you read today, `records/bugs.md`, stays where it is, but Bonsai writes it from the
files (`bonsai check --write`), marked "generated, never edit by hand", and the guard refuses a hand edit of it once it is (a register not
yet moved stays an ordinary file, never overwritten), so a reader like the studio's bridge knows to skip it. Agents work with bugs through one command, `bonsai bug`: `add`
takes the next free id and writes the file; `fix`, `wontfix`, `watch` and `reopen` change where a bug stands; `edit`
changes its text; `list` and `show` print them (`--json` for agents). Every id is `BUG-` and a number, in every
project. **`bonsai bug` is the one way a bug's status changes, in every project, with or without the studio** (your
word of 19 Nov: Bonsai is a core standalone technology): the guard refuses a hand edit of a bug's status line in
every project and names the `bonsai bug` command, and the `status_writes` switch that tasks follow does not apply to
bugs. So Bonsai logs every bug move with who made it, and the bug file keeps who filed it and who fixed it. `bonsai
status --json` lists the bug folder with its place and statuses, so the studio reads the
files and needs no bug command. There is no import: you tell each project's agent to move its register, and base's
new `bug` skill tells that agent how. The workflow pack's `bugs` kind and skill give way to Bonsai's. It changes one
line of the contract you approved on 7 Oct ("Bonsai has no apply and no task-status command"): tasks stay as they
are, and Bonsai gains a bug command that writes a bug's status. It
ships as Bonsai 1.1.0, base 1.1.0 and workflow 1.1.0, each tagged by you.

**Choices that are yours.** None left. Decided 19 Nov: bug moves always through `bonsai bug`, never the studio's
command ("always bonsai bug"), so an old fixed bug is carried over by `bonsai bug add --was TB-012 --number 12 --status
fixed --commit <sha>` in every project; Bonsai's own register moved by the orchestrator after the release; `watched`
kept as a fourth status.

**Risk.** It changes the formats (a new kind and format, the log's words, the status format's document list, the
settings file's places), the guard (bug files and the generated page) and two packs, so a fresh Opus verifier reads
each stage before landing. The task stops and reports blocked if the guard's status-line rule cannot cover bug files
without loosening what it holds for tasks, or if a project on the old workflow pack (which still declares `bugs`)
would fail to link with the new Bonsai: either comes back to you as a question, not a workaround.

**Size.** About 18 to 26 hours of agent time in three stages, stop line 34 h. Nothing to set up first. At the end you
push three tags (Bonsai `v1.1.0`, base `base-v1.1.0`, the workflow repo's `v1.1.0`) and approve the release run.

### Approach

**Stage 1: the format, the kind and their places** (T-6024).

1. `formats/schemas/bug.schema.json` (`bonsai.bug/1`): `format`, `id` (`^BUG-[0-9]{3,6}$`), `title`, `status`
   (`open`, `fixed`, `wontfix`, `watched`: choice 3), `area`, `where`, `found_by`, `filed_by`, `fixed_by`,
   `fixed_in`, `task`, `was`, `why`, `created`, `closed`, `labels`; free body. Every field documented with an
   example. A carried-over bug's dates: `created` the old row's date where it names one, else the day of the move
   with `was` set; `closed` null when no date is known (the schema allows it only with `was`). `bugs.schema.json`
   (`bonsai.bugs/1`) for the page. `formats/manifest.json` set 14, `formats/README.md`, examples and trick files;
   the formats table in `internal/format/format.go` (near line 139).
2. Places. `internal/format/workspace.go` `Documents` gains `Bug` (the folder); `workspace.schema.json` makes `bug`
   optional (every bonsai.yaml today lacks it): absent, the folder is `bugs/` beside `documents.bugs`'s file; both
   absent, `work/bugs.md` and `work/bugs/`. `bonsai init` writes both lines. base:workspace documents them (stage 3).
3. `internal/workspace/documents.go`: `bonsaiKind` gains statuses, moves and a stamp (today it has none); kinds
   `bug` (statuses above; agent moves open to fixed/wontfix/watched, watched to open/fixed, fixed and wontfix to
   open; stamp `fixed: closed`, `wontfix: closed`) and `bugs` (the generated page). The old workflow pack's `bugs`
   kind is set aside with a warning naming `bonsai pack set`, in each place that meets it: `declares.go` (near
   182), `checkpack.go` (near 678), `DocKinds` (138-168: listed once, Bonsai's), and the guard's kind reading
   (`tripwire.go` 103-113). A test links a project on workflow v1.0.2 with the new Bonsai.
4. `internal/engine/tables.go`: the page built from the bug files, byte-stable; the `tables` warning when it lags;
   `generated.go` and base:generated-files name it (kept, never cleaned) and the id lock file
   (`.bonsai/local/bug.lock`, removed after each `add`; a stale one older than a minute is taken over). `bonsai
   check`: each bug file against its schema, two files with one id (findings). **A hand-kept page is never
   overwritten:** `--write` builds the page only when it is missing or carries the generated marker (`format:
   bonsai.bugs/1`); a page without the marker (every project before it moves its register) is left as it is, with a
   warning `bugs-not-moved` naming base:bug, never a finding, so rung 0 stays green. A marked page that differs from
   a rebuild is the `tables` warning, as the tasks table is. Tests: an unmoved register through `check --write`
   comes out byte for byte the same; a marked one is rebuilt.
5. `status --json`: `bug` and `bugs` in `documents`, nothing read per bug; `status.schema.json`. The contract: 7.3
   (the two kinds; "Rows ... are not contract" goes), 7.5 (a generated page outside `.bonsai/`, at its declared
   place, held by the guard against hand edits and by rung 0 against branches **only while it carries the
   generated marker**: an unmarked, hand-kept register stays an ordinary file, edited and deleted as today; rung 0 reads the marker
   from main's copy, so a branch that adds it passes and one that strips it is refused), 10's
   opening line (the bug command, the
   director's words of 19 Nov).

**Stage 2: the command, the log and the guard** (T-6025).

6. `cmd/bonsai/bug.go`: `bonsai bug add|fix|wontfix|watch|reopen|edit|list|show`, `--json`, unattended, each
   refusal with its next step. Every writing subcommand writes the main checkout's folder wherever it runs (a
   worktree's copy is never written, as tasks are held to main); `list` and `show` read it. `add` takes the highest
   number in the folder plus one, never reused, under the lock file of step 4 (Windows: renames retried on busy). `fix
   --commit <sha>` refuses a commit the repo lacks. `show` finds a bug by its `was` too. The carry-over: `add --was

7. Every move command writes the status, its stamp and its fields itself, whatever `status_writes` reads: the
   switch is for tasks only and `status_command` is never named for a bug (the director, 19 Nov). Contract 10's

8. The log: a `bug` event in `internal/format/log.go` (the words near line 64), contract 8.2's list and
   `log.schema.json`'s text, for each add, carry-over, field change and move Bonsai's command makes, who from the
   recorder's identity (role and task), the bug's id in `target`, the move in `reason` (the record has no from/to
   fields; none added). Every bug move is Bonsai's own command's, so every one is logged.
9. The guard: `documentOf` and `bonsaiFormat` gain the bug kind; the status-line rule (`tripwire.go`, `rules.go`

   generated page refused to hand edits and deletes in both modes, as `.bonsai/tasks.md` is, but only while the file
   carries the marker (not a path rule like `floor.go:44`: the marker read when the call is judged); an unmarked
   page is free. Guard tests: an unmarked page is edited and deleted, a marked one is refused both; rung 0 tests: a

   Tests in both modes, on both OSes.
10. `--help`, `help --json`, the reference page (`docs/reference/lists.md`), and the `bug` line in

### Choices made, and what lost

| Choice | Alternative | Why this one |
|---|---|---|
| Bug is Bonsai's own kind | Keep it the workflow pack's, with a declared row shape | A format every project and the studio read is Bonsai's, as tasks are |
| One file per bug, the page generated | Commands that edit the one markdown table | Two agents filing at once never clash; no hand-kept table to drift |
| `BUG-` everywhere (the director) | A prefix per project | One pattern, as tasks and runs have; the old id kept in `was` |
| No import command (the director) | `bonsai bug import` | Each project's agent moves its register by base:bug |
| Ids taken in the main checkout under a lock | Ids taken on the branch | Branches would both take BUG-146 |
| The page at `documents.bugs`, the old path | `.bonsai/bugs.md` beside the tasks table | 15 run reports and memory notes link the old path; the guard and rung 0 hold it there instead |
| `documents.bug` optional, defaulted beside the page | Required, as Bonsai's other keys are | Every bonsai.yaml today would fail its schema |
| Bug moves always by `bonsai bug` (the director) | Following `status_writes`, as tasks do | Bonsai stays standalone; bugs carry no approval for an outside tool to record; every move logged |
