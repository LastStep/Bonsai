# Plan: a checkout with Git LFS climbs clean (1.0.1 candidate; the studio's B-053, Bonsai's BUG-054)

Two readers. **The director** reads the first part only (down to Size). The **builder and verifier** read the rest.

## For the director (plain words)

**What is wrong.** In a project that keeps files in Git LFS (Mimas: 216 images and fonts), every climb is green but
its result says `dirty: true`. A dirty result proves no commit, so the stop gate (stop-dirty), the bless offer and
the landing rule all refuse it. Mimas can never land a proved piece.

**Why.** Reproduced on 26 Oct on both sides with the installed 1.0 (WSL with a stand-in LFS filter; Windows with
real git-lfs 3.4.1 and `bonsai.exe`): one LFS image, committed, untouched, `git status` empty; the climb is green and
`dirty: true`, naming the image: "its contents differ from HEAD's, though git status shows no change". To catch an
agent hiding an edit from git, the dirty check compares every file's bytes with what HEAD holds, with every git
filter switched off, since a filter could lie. For an LFS file, HEAD holds a small pointer and the folder holds the
real file, so they never match. This was known and written down as a limit (BUG-054, "after 1.0"). Line endings are
not hit: CRLF checkouts from `autocrlf` or `eol=crlf` climb clean on both sides (also tested).

**The fix.** Check an LFS file the way LFS itself defines it, without trusting LFS or any filter: HEAD's pointer
names the real file's SHA-256 and size; Bonsai hashes the file in the folder and compares. Equal means the file is
exactly what the commit names, so it is clean; any other byte, or a changed executable bit, still reads dirty. Only
files the commit itself puts under LFS are checked this way (a local setting outside the commit cannot add one). Nothing new is trusted, and git-lfs
need not be installed. **Not** the fix proposed in the report ("ask git with its filters on"): that reopens the hole
the check was built to close (a filter can make an edited file read as unchanged).

**What stays as it is.** git-crypt and any other filter still read dirty (Bonsai cannot check those without the key
or the program); the limit is kept, under its own bug. No format, schema or contract text changes; no recorded
result changes (old results stay as written; new climbs in LFS projects read clean).

**Size.** One builder (Opus: it is in the dirty check and rung 0, guard areas) about 4 h; a fresh Opus verifier about
1 h, security and tests lenses; landing with CI about 0.5 h. About **5.5 to 6 h** in all (the plan review raised it
from 4.5 h: three holes in the first draft, now closed below). The test floors rise by the new tests
after it lands.

**Your decisions.** (1) Approve this plan. (2) Later, whether it ships as 1.0.1 (a release is yours).

### The change

1. **`internal/vergit/lfs.go`** (new): `lfsPointer(blob []byte) (oid string, size int64, ok bool)` reads a Git LFS
   pointer by the spec v1, strictly: under 1024 bytes; first line `version https://git-lfs.github.com/spec/v1`; then
   `oid sha256:<64 lower hex>` and `size <decimal>`, keys sorted, each line ending in LF, nothing else. A pointer with
   `ext-` lines (pointer extensions) or the old `hawser` version is not read (the file stays dirty).
2. In `contents()`, after the fresh-index status: the entries whose status is a worktree modification only
   (` M`, never `D`, `T`, or a staged change) are candidates, dropped after `seen` is built so `converted()` does
   not recheck them. **The attribute comes from HEAD's commit only** (plan review, blocking 1): `check-attr --cached
   -z --stdin filter` through the fresh-index runner (the index is HEAD's tree), with `core.attributesFile` pinned to
   the null device for that call, and the rule switched off for the whole read (every candidate stays changed, the
   reason saying why) when `info/attributes` holds any line that is not blank or a comment. Then one `cat-file
   --batch` call for HEAD's blobs (ids and modes from `headTree()`). A candidate leaves the changed list only when:
   its HEAD entry is a blob of mode 100644 or 100755 that parses as a pointer; the file, **opened first**, is a
   regular file by the open handle's stat, its size equals the pointer's; **its executable bit matches HEAD's mode
   wherever this package pins `core.fileMode`** (plan review, blocking 2; where it is not pinned, as on Windows, git
   cannot see the bit either); and its SHA-256, streamed from that handle (`io.Copy`), equals the oid. The hashing
   loop checks the read's deadline between files. A file that cannot be read stays changed, its reason saying so.
3. The same helper for ` M` entries of the first read (plain status) and of **rung 0's own `git status`**
   (`internal/rung0/git.go:155-172`; plan review, blocking 3), so a verified LFS file is neither shown nor judged.
4. Submodules: `sub.tree` calls `contents()`, so they get it; one test proves it.
5. The `Hidden` reason and the text's next step for a path under a filter that is not verified: say "under the
   filter <name>, which Bonsai cannot check; a checkout with it reads dirty" instead of today's `git rm --cached`
   advice, which does nothing for a filter (`internal/ladder/text.go`).
6. Docs in the same commits: the known-limits bullets in `vergit.go` and `Tree`'s comment (LFS verified by its
   pointer; git-crypt and other filters still dirty); `docs/features.md`'s Git integrity row; `records/bugs.md`:
   BUG-054 fixed by this task, a new bug for git-crypt and other filters (Open, a known limit), and the
   newtests/check rows above as notes. No `formats/`, `design/` or `bonsai.yaml` change.

### Security argument (for the verifier to attack)

A file is dropped from the changed list only when its bytes hash to the SHA-256 that HEAD's committed pointer names,
at the size it names. That is the content the commit names; a test reading the file sees exactly it. Nothing from
the index, a filter, git-lfs or the user's configuration is trusted. Which files are tried comes from HEAD's committed
attributes only: a local `info/attributes`, an ignored `.gitattributes` or a configured attributes file cannot add
one (else a pointer committed as plain text would pass while a clone gets the pointer). The executable bit must match
HEAD's mode. An edit to the committed `.gitattributes` itself shows as a change. Cost: each LFS file is hashed at every climb's start and end and
once in rung 0; the run report measures it on a repo with 200 files of 1 MB.

### Tests (all with `t.TempDir()`, no git-lfs needed: the pointer blob written by `git hash-object -w` and
`update-index --cacheinfo`, or by a stand-in clean filter in the repo's config as in `repro-wsl.sh`)

- An LFS file committed, the folder holding its real bytes: `Tree` not dirty, nothing hidden (the bug's case).
- The same file edited, same size: dirty, named. Different size: dirty.
- Pointer with an `ext-` line; pointer with upper-case hex; a blob under `filter=lfs` that is no pointer; the
  folder holding the pointer itself (not smudged): clean (git's own read is equal); the file replaced by a folder or
  a link (not on Windows: say why): dirty.
- No `filter=lfs` attribute, HEAD holding a pointer, the folder its content: dirty (only LFS files are tried).
- **The attack from the plan review:** a pointer committed as plain text at a path the committed `.gitattributes`
  does not put under LFS, `filter=lfs` added for it in `.git/info/attributes`, the real bytes in the folder: dirty.
  The same through an ignored untracked `.gitattributes` and through `core.attributesFile` in the repo's config: dirty.
- **Mode:** HEAD 100644, the file made executable, bytes unchanged: dirty where `core.fileMode` is pinned (not on
  Windows, which keeps no executable bit: the test says so).
- Just committed (first read's ` M` on Linux): clean.
- Staged change on an LFS file: dirty.
- Stale stat times (the file touched after the index was written, LFS only in a config the fixed env does not read):
  clean when the bytes match.
- A submodule holding an LFS file: clean; edited: dirty, named from the top.
- A SHA-256 repository (`git init --object-format=sha256`), where git supports it: clean.
- git-crypt-like filter (a clean filter that is not LFS): still dirty, with the new reason.
- `lfsPointer` table test of the spec's cases.
- Ladder level (`internal/ladder`): a climb in such a repo reads `git.dirty` false; rung 0 with the LFS file under a
  protected path stays green, with fresh and with stale stat times.
- Cost: 200 files of 1 MB, timed at a climb's start and end and in rung 0, in the run report.
- The repro scripts run again with the built binary on both sides (WSL and Windows `bonsai.exe` from the branch):
  LFS clean; touched; edited dirty.
